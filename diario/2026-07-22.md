A day dedicated almost entirely to the marketing-calendar feature, spec-first: first closed out 3

## What I did

### 1. Resolved 3 open design questions (morning, spec first)
- A dedicated module for reading/writing a "processed" status flag that deliberately bypasses the
  shared manager function it would normally go through — reuse would have triggered an unrelated
  side effect on unrelated records.
- Field sanitization/truncation before a bulk insert, so one oversized field from an LLM response
  never fails an entire calendar's pre-population.
- A recurring background healer (matching an existing precedent elsewhere in the codebase) that
  retries stuck syncs up to a bounded retry count.

### 2. Marketing calendar — automated pre-population + claim redesign (morning)
- Replaced click-only population with two write paths: an independent background task converts a
  source markdown calendar into structured entries via an LLM call and pre-populates every entry,
  while the existing click-time path claims the matching row by a normalized fingerprint instead of
  a client-computed identifier that isn't reproducible server-side. New table with a surrogate key,
  generated fingerprint columns, and a bounded-retry healer task.
- Verified live end-to-end against a real database and a real background worker (fingerprint claim
  collisions, flag read/write, truncation, healer retries).

### 3. Read endpoint + a fast-path for real IDs (late morning)
- Wrote the spec: the frontend already had an active calendar screen consuming mock data with a
  comment inviting a real hookup. Since there was no live contract to preserve, designed the ideal
  shape instead of perpetuating a fragile client-side hash.
- New read endpoint exposing every calendar entry for a given context, same auth pattern as the rest
  of that module. The write path gained a fast-path: a real client echoing back a numeric ID claims
  the row directly; a non-numeric legacy identifier falls through to the fingerprint path unchanged.
- Verified live end-to-end via a real HTTP round trip, including the not-found path.

### 4. Routed the sync through the LLM fallback system + a real truncation bug (afternoon)
- The calendar-sync task now calls the assistant feature's shared multi-provider call, which
  automatically tries a health-gated sequence of fallback providers, instead of calling one provider
  directly with zero fallback. Verified end-to-end against a real run: during an ongoing outage of
  the primary provider, the fallback sequence correctly tried each backup provider in order, recorded
  the failure cleanly (no partial writes), and let the retry healer pick it up later.
- Root-caused a real, independent bug: a fallback provider returned real content but got cut off
  mid-response at the old token cap, with no valid closing syntax — a genuine bug, not just a symptom
  of the outage. Increased the token budget and the timeout accordingly. Full end-to-end confirmation
  is blocked on the primary provider's outage being resolved — the same model that revealed the bug
  now times out before finishing the larger response, so it's not yet clear whether that's normal
  latency variance or a still-tight budget.
- Merged, closing out 3 days of work on the calendar feature.

## Learnings / technical decisions
- Routing a "processed" flag through a dedicated module instead of a shared manager avoided a hidden
  side effect the shared path would otherwise trigger unconditionally — sometimes the "correct" option
  per convention has a side effect that makes it the wrong choice for a specific case.
- A provider outage can hide a second, real bug behind it — worth continuing to investigate even
  after finding an "obvious" cause that explains the surface symptom.

## What I could do better
- The token-budget fix has no full end-to-end confirmation yet because the primary provider is still
  down — it's a fix applied somewhat blind until the provider recovers. Should have flagged explicitly
  in the tracking issue that this needs a follow-up verification once the provider is healthy again,
  so it isn't marked done prematurely.
