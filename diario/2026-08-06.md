## What I did

### 1. Designing the entitlement spec (morning)
- Wrote a full spec with seven architecture-decision records: why a new "payment due" state is
  different from a payment processor's own dunning status, why entitlement should always derive from
  live dates rather than a stored status field (avoiding an up-to-one-hour window of incorrect state
  between a scheduled job and a webhook), and the rollout order across four product areas.
- Branch housekeeping before starting: indexed yesterday's fix into the integration branch, normalized
  line endings before opening the new feature branch.

### 2. Entitlement foundation: status enum, service, scheduled job
- New subscription-status value for "payment due", with a tolerant fallback so it never breaks older
  stored records with unexpected status strings.
- A later verification pass found a real case the first fallback didn't cover: several real records use
  a legacy misspelled status value (matching the payment processor's own spelling) that would have
  fallen through to "unknown" without an explicit alias — a real regression I introduced myself, caught
  and fixed before moving on.
- New entitlement service — the single source of truth for "can this project still write right now":
  effective-end date takes the maximum across the project's own plan and any live sub-subscription;
  grace period comes from a real per-plan catalog, not a global constant; a short-lived cache with
  explicit invalidation.
- Added a "payment due" branch to the existing subscription-expiration scheduled job: phase one moves
  active subscriptions to payment-due instead of straight to expired; phase two promotes payment-due
  subscriptions to expired once their grace period elapses — verified against a real record, reversibly.
- 16 unit tests for the entitlement service: a state/date matrix, grace-period tiers, a rule protecting
  a still-active sub-subscription even after its parent plan expired, defensive cases, and cache
  behavior.

## Learnings / technical decisions
- A reusable guard with swappable resolution strategies keeps one blocking algorithm instead of four
  near-duplicate implementations (one per product area) with subtle differences.
- Deriving entitlement from live dates, never from a stored status field, is the design choice that
  makes the rest of the feature verifiable — there's no clock window where a scheduled job and a webhook
  disagree about what the displayed state should be.
- Deliberately pausing after two of four areas to shift focus to the frontend (instead of finishing
  backend first) was an explicit decision, documented with the exact resume point — not a half-finished
  cutoff with no plan.
