**Context:** recovered a real bug that had gone undetected for days — a fix that looked "merged" on

land on the shared branch: an earlier pull request had merged against a base branch that was itself
absorbed into the integration branch moments before, orphaning the fix's commit. Reapplied cleanly,
verified against the full test suite and static analysis.

### 2. End-to-end regression suite
Added new end-to-end tests covering a payment-status banner and its purchase-intercept behavior, plus
an active-project regression case.

### 3. Shared status-display logic promoted to SDK
Deduplicated plan-status-to-visual-tone logic that had drifted into separate copies on web and mobile,
moving it into a shared SDK package.

### 4. Spec work: payment-due entitlement
Merged a design spec (open since early August) documenting the read-only mode a project enters when a
subscription lapses without renewal.

## Ops
Three pull requests opened, one bug closed.

## Learnings / technical decisions
A pull request marked "merged" doesn't guarantee its commit lives on the real target branch if there's
a merge race between sibling branches — worth verifying real ancestry directly when something "already
merged" keeps behaving as if it weren't.
A separate integration branch used for a different initiative stays frozen indefinitely, by an external
decision rather than a technical one.

## What I could do better
The orphaned-fix bug sat undetected since the weekend because nothing verified that a "merged" fix
actually lived on the shared branch — a routine post-merge check would have caught it sooner.
