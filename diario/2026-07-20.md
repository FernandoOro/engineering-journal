# 2026-07-20 (Monday)

**Context:** shipped a complete plan-management modal (seats, clients, plan deletion) for a fintech
SaaS platform (client), then added a plan-upgrade option on top of it and caught 4 real bugs while
testing it against a real (non-demo) plan — plus a backend bug where dead code was silently masking
a pricing error.

A day about closing out a full surface: in the morning I built a plan-management modal from scratch
(client-side data layer, UI, gating by real availability, add/remove members) and merged it before
noon. In the afternoon I added a third option to the same modal — upgrading the current plan — and
while testing it against a real plan found and fixed 4 distinct bugs in under 40 minutes, the kind
that only show up against real data, not a demo happy path. In parallel, on the backend, a bug that
had been masked by dead code for a while.

## What I did

### 1. Plan-management modal — seats, clients, delete (morning)
- Wrote the requirements spec before touching code.
- Client-side data layer: 8 new actions surfaced from the backend contract, all already implemented
  server-side — pure client-side surfacing.
- Wired a previously dead "Manage" button to a two-level modal: plan summary → delete plan (confirm,
  soft-delete, no refunds) | manage seats & clients → buy (checkout) / view list / add by email.
- "Add Seat"/"Add Client" now reflect real availability from the backend instead of a heuristic based
  on plan type.
- Two real UI bugs: a missing flex-direction on a container glued a title and its caption onto one
  line; emoji icons replaced with SVGs matching the rest of the icon system.
- Added a remove-seat/client action with an in-modal confirmation step (not a native browser
  confirm).
- Resynced with a large integration merge that landed on the main branch; verified beforehand in a
  disposable worktree that there was no real conflict.
- Merged. Closed the tracking issue.

### 2. Plan-upgrade option + 4 bugs found testing against a real plan (afternoon)
- Wrote the spec for the upgrade option first.
- Added a third modal option, gated on the backend's own upgrade-eligibility endpoint (never a
  hardcoded plan-type check).
- **The spec itself had the bug:** the real route required a trailing wildcard the initial research
  missed, and the implementation faithfully inherited the mistake.
- Direct consequence: the eligibility check was hitting a 404 (silently swallowed by the effect that
  called it), so the upgrade option always rendered disabled.
- The modal crashed to a blank screen on a real (non-trial) plan: per-cycle cost fields are
  legitimately nullable on the backend, but the client typed them as plain numbers — calling a
  formatting method on `null` threw. Also, the flow auto-selected the first option instead of showing
  a selection step first, unlike the legacy flow this feature replaces.
- The backend's generic upgrade-path engine also lists product variants this platform doesn't
  currently sell — filtered those out by a product-tier flag.
- That filter used the wrong signal (a field that's being phased out); fixed to gate on whether an
  option actually has a real chargeable amount instead — correct regardless of what the backend's
  registry lists.

### 3. Backend — dead code masking a pricing error
- A cost-calculation function had an unconditional early return sitting at the same indentation as
  its intended fallback for undefined cases — dead code, so any undefined upgrade combination
  silently returned an empty, all-null result instead of a clear error. Verified live against both
  non-production and production that this masked exactly the symptom reported from the frontend
  side. Spec for the bug written the same day it was found, not batched later.

## Ops
- 2 merges to the shared integration branch.
- 3 tracking issues closed or in the process of closing.

## Learnings / technical decisions
- The 404 bug in the upgrade-eligibility check was born in the **spec**, not the code: the initial
  research never validated the route against the real running server, and the implementation copied
  a wrong spec detail faithfully. Spec-driven development only protects you if the spec itself gets
  validated against reality, not just written down.
- Gating UI on real backend availability (context/pricing) instead of a plan-type field is more
  robust because it doesn't depend on that field continuing to mean the same thing tomorrow.

## What I could do better
- One fix corrected another fix from 10 minutes earlier that, by its own commit message, already
  knew it was using the wrong signal — I used it anyway as a quick shortcut and had to revisit it.
  Verifying against the right field the first time would have saved the second pass.
- The dead-code bug could have surfaced earlier: the existing tests for that file weren't exercising
  the real code path (fixed the next day) — a broken test nobody notices is as dangerous as no test
  at all.
