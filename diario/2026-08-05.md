### 2. Name-search feature — web first, then mobile, same day
- Wrote the spec: one section of a projects screen already had backend support for search; a second
  section didn't have a search parameter yet, so it's designed as a client-side filter with a bounded
  auto-paginate sweep, so a search never silently reports zero results while an unloaded page could
  still contain a match.
- Web implementation: debounced input, per-query request correctness, an accessible live region
  announcing result counts, escape-to-clear. Designed with an architecture-review pass, then reviewed
  by a language-focused review pass that caught and fixed a real race condition in the same commit (a
  stale page could merge in after a newer search had already settled). 73 new/updated tests, full
  workspace suite green.
- Refactored the shared search-matching logic out of the web app into a common package, for reuse from
  mobile — verified no behavior change (both the shared-package tests and the web app's own tests
  green).
- Wrote the mobile port's spec — investigated the mobile app's actual architecture first (a different
  state-management approach than web), so this wasn't a literal port: promote the shared helper, design
  an auto-paginate sweep against a store method that doesn't return a page, and a fallback for a
  Unicode-normalization gap in the mobile JS engine.
- Shipped the mobile port: a first debounce hook, a first accessible live-region pattern, and a shared
  search-field component new to this app — 91/91 tests green.

### 3. Infrastructure investigation: a broken container build (unplanned)
- A shared container image (serving several web apps) had been failing to build for about a week and a
  half, and once fixed to build, failed to actually run. Found and fixed six distinct root causes, each
  reproduced and verified end-to-end (build + run + a live health check), not just inferred from reading
  the build file: a stale file reference left over from an unrelated dependency change; a missing
  shared config file the build stage needed; an illegal TypeScript configuration combination across five
  packages that had never actually compiled, masked by a non-blocking type-check step in CI; a missing
  build-output path setting that left one app's production bundle unable to find its own dependencies;
  a server file path that moved without updating the process supervisor's config; and a log directory
  ownership issue that crashed the reverse proxy on boot. Independently reviewed by a second review
  pass, no blocking findings.

## Learnings / technical decisions
- Designing against a platform's actual architecture instead of literally porting another platform's
  pattern avoided rework — the mobile solution ended up genuinely different (using its query cache
  instead of manual request cancellation) and worked on the first try.
- A non-blocking type-check step in CI can mask a broken build for well over a week without anyone
  noticing — five packages had an illegal configuration well before the container build broke, and it
  only surfaced when someone actually tried a real build.

## What I could do better
- The container build was broken for 9 days before anyone ran a real end-to-end build — none of the six
  bugs were hard to find, they simply weren't exercised. This codebase is still missing a periodic real
  build-and-run check instead of trusting that the code "looks right" in review.
