### 2. Single-container Dockerization of 4 web apps (rest of the day)
- One image for 4 separate web applications, following an infrastructure decision to consolidate them
  into a single deployable unit:
  - **Build:** a multi-stage build scoped to exactly the 4 web apps (a separate mobile app explicitly
    excluded), with a runtime stage running a reverse proxy and a Node process supervisor together.
  - **Reverse proxy:** per-app routing rules, an origin-verification header check (rejecting anything
    without it), single-page-app fallback routing, cache-control tuned per asset type, a
    content-security-policy per app, and a health-check route proxied to the real running process.
  - **One app's build config:** switched its build script to a more stable bundler mode after the
    default one failed to detect the monorepo's workspace root correctly.
  - **CI:** a new build-only job running on every PR (no push), plus separate deploy workflows for
    each environment using short-lived cloud credentials instead of long-lived secrets, scoped to
    their own environment and never triggered by a pull request.
  - **Local verification: incomplete.** 3 real build attempts in this sandbox — two caught genuine
    configuration bugs along the way (now fixed), the third failed purely on an unreliable network
    path to the package registry after several minutes of retries. The build logic is validated up
    through that step; the final copy paths for the production build remain unverified empirically
    until a real build completes — the next real verification is the CI build job running on
    GitHub-hosted infrastructure with reliable networking.
  - Wrote the accompanying spec/plan/tasks documentation for this feature; still needs to be
    committed to the spec repository — carried into next week.

## Learnings / technical decisions
- When a build fails on networking rather than logic, it's worth documenting exactly how far
  verification got (here: everything up to the dependency-install step) rather than leaving the PR in
  an ambiguous "untested" state — so the next verification pass (CI, with reliable networking) doesn't
  have to repeat the same diagnosis from scratch.
