# 2026-07-23 (Thursday)

**Context:** designed and built a full multi-conversation feature end-to-end (backend, client SDK,
frontend), proposed and adopted a new branch-integration model for the team, and shipped a real
production fix for an LLM-provider fallback system.

The busiest day of the week. Started with the spec for a multi-conversation feature — replacing a
temporary single-thread workaround — and from there built all 6 backend layers in a single morning
(status/rating types, schema columns, migration, data-access layer, services, endpoints). In
parallel, the team adopted a new integration-branch model that I proposed and merged. In the
afternoon I carried the same feature into the frontend: an active-project store, the client SDK, and
retiring the old single-thread hack. Closed the day with a real production fix: the LLM-provider
fallback system wasn't actually protecting requests in practice, even though the function that should
have done it already existed and was tested elsewhere in the codebase.

## What I did

### 1. Multi-conversation spec (early morning, spec first)
- Wrote the backend spec (data model, migration, endpoints, services) plus the frontend/SDK spec,
  replacing a temporary single-shared-thread workaround.

### 2. Backend — multi-conversation, all 6 layers in one morning
- Status/rating enums for conversations and messages.
- Schema columns for project association and message state.
- A migration (columns, a foreign key with safe null-on-delete behavior, check constraints, an
  index, a guarded backfill) — **additive only, not applied to any live database by this change**,
  still pending an apply step.
- Extended the data-access layer: list/create/update for conversations, a richer message listing
  (active records only), rating, and soft-delete.
- New service layer: business logic for listing/creating/updating conversations and for
  sending/streaming/rating/deleting messages, resolving the owning project to gate feature flags and
  rate limits correctly.
- New endpoints, thin and delegating to the services. Legacy aliases keep their exact existing
  behavior with a deprecation signal. Opened for review — the verification checklist (lint, e2e
  tests, migration review, gate resolution on the new streaming endpoint) is still in progress and
  will be worked through before merge.

### 3. Adopted a new branch-integration model (morning)
- Feature branches now cut from a shared integration branch, PRs merge there, and releases promote it
  to the production branch — mirroring a model already proven on another repo. The production branch
  stays protected and deploy-only.

### 4. Frontend — active-project store + a code-review pass (mid-morning)
- A small, persisted store for "which project is currently active," wired to the project switcher so
  the selection survives a reload.
- Addressed review feedback on that change: centralized the write path into one shared hook instead
  of wiring it at each call site, so desktop, mobile, and deep-link entry points can't drift out of
  sync; cleared the persisted selection on sign-out so a second user on the same browser doesn't
  inherit the previous one's project; covered the change with real (non-mocked) test assertions.

### 5. Frontend — SDK + opening real per-conversation threads (afternoon)
- New client SDK methods and wire types for the multi-conversation endpoints, reusing the existing
  authenticated transport layer, with request/response tests for each.
- Replaced the single-shared-thread routing with real per-project, per-conversation IDs: each history
  entry and "new conversation" action now maps to its own distinct thread instead of collapsing into
  one shared conversation. Fixed a related display bug where real backend text (names, previews,
  dates) was being force-resolved as translation keys instead of rendered as literal text. Removed
  the now-dead single-thread persistence hack.
- Fixed the message-send path to call the new real per-conversation endpoint instead of a legacy
  alias whose rate-limit gate silently no-op'd whenever the ID it received wasn't a real project
  identifier — which a genuine per-conversation ID never is — so usage limits were being bypassed for
  every message in a new conversation.

### 6. Production fix — LLM fallback system wasn't actually protecting requests (afternoon)
- A provider-exhaustion detection function already existed and was proven in another part of the
  codebase, but was never wired into the 3 places the assistant feature actually catches a
  primary-provider failure — so the carousel's own skip logic never engaged, and every message
  re-discovered the same known outage independently, burning the full request timeout before a
  backup provider ever got a turn. Also fixed a local-environment configuration gap that was breaking
  real-time updates and the fallback system's own health lookups in the local stack.
- Opened for review with a new regression test covering the fix directly — the full existing test
  suite for that area passes; a lint pass is still pending before merge.

## Learnings / technical decisions
- The fallback-protection function is the same pattern I've run into in previous weeks: a correct
  function only protects the system if it's actually called from every real place that needs it, not
  just the one it was originally written for. A fix applied in one spot left three sibling call sites
  exactly as broken as before.
- Centralizing the active-project write path into one hook, based on a code-review observation, is
  the same "single source of truth" principle I learned last week with two chat surfaces that had
  drifted apart.

## What I could do better
- I opened a large amount of well-scoped, spec-first work across two repos today, which is good — but
  by end of day several of those PRs were still moving through review rather than merged, including
  one with a verification checklist not yet fully worked through. Next focus: prioritize finishing
  verification and merging what's already built before starting the next branch.
