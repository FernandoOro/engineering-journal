# Week 2026-W34 (Mon Aug 17 – Fri Aug 21)

Two threads this week: **closing out an entitlement/billing feature line** end to end across
frontend and backend (plan renewal, past-due enforcement, an "expired project" content gate), and
**starting a real migration to a rebuilt backend** — the first production surface cut over to a
new architecture, with two real bugs caught by live verification and one self-inflicted
compatibility regression reverted the same day it landed.

## Frontend / client SDK (fintech SaaS platform — client)

- **Done (Monday — plan-renewal UI):** a pure eligibility policy (a trial plan never renews); a
  "renew" action added to the existing plan-management UI; a real mobile bug fixed where an
  expired/past-due plan status was being coerced into "active" before it ever reached the screen.
- **Done (Tuesday — five real navigation/project bugs + a silent chat bug):** a project card
  opening the wrong project; a deep-link sweep that stopped after the first page of results; a
  coupon sending the wrong billing-cycle value; a chat drawer that silently swallowed a user's
  first message and never surfaced the payment-required dialog it should have.
- **Done (Wednesday — full mobile rollout of the payment-gate pattern):** the same
  payment-required interception seam wired into every remaining write action across the app's
  main product areas on mobile; a project-selector bug where one feature ignored the user's
  active-project choice entirely.
- **Done (Thursday — "expired project" content gate + a progress-status feature):** a gate that
  replaces only the content area (never navigation, renew/upgrade, or project-switching) when a
  project is fully expired; a cache-invalidation hook tied to that new error state; a real bug
  caught in manual testing where the "renew" call-to-action linked to a view that was itself
  blocked; a pending/ready/failed progress-status feature shipped on web, then mobile, same day.
- **Done (Friday — closing out the payment-gate rollout + starting the backend cutover):** three
  more write actions found silently swallowing the payment-required error, reproduced live and
  fixed with the same existing pattern; then the start of a client SDK for the new backend's auth
  API, built by reading its real request/response contracts directly rather than assuming them;
  the app's auth surface switched over unconditionally to the new client — a staged, full cutover
  with no runtime toggle — left open at week's end.
- **Technical decisions:**
  - Reuse the same "payment required" interception pattern everywhere a new write action needed
    it, instead of a bespoke error-handling path per screen.
  - The "expired project" gate wraps only page content, never the app chrome — renew, upgrade, and
    switching projects stay reachable even when a project is fully blocked.
  - The backend-auth cutover is staged and complete per surface, with no dual-backend runtime
    flag — a deliberate reversal of an earlier design that planned to run both backends side by
    side (see process section below).
- **Mistakes (root cause):** two more instances this week of the same silent-failure shape flagged
  as debt last week — an error handler swallowing a real error without logging or surfacing it.
  Root cause is unchanged: when the payment-gate pattern was first introduced, its call sites
  weren't audited exhaustively in one pass, so each surface finds its own missing case
  independently, days apart.
- **What I learned:** reproducing a real backend error with a direct request against a live
  instance still finds bugs in minutes that a test suite missed — worth doing before calling any
  fix complete.
- **Where I'm weak:** the silent-failure pattern was explicitly named as debt worth fixing
  immediately last week, and it recurred twice more this week instead. The systematic sweep that
  would have caught all of it in one pass still hasn't happened — I keep finding instances
  reactively instead.
- **Next-week focus:** finish and merge the backend-auth cutover; do the exhaustive sweep for the
  remaining silent-failure call sites instead of waiting for the next one to surface; follow up on
  a real intermittent login bug found (but not yet fixed) while verifying the new backend live.

## Backend — MVP (fintech SaaS platform — client)

- **Done (Monday — plan renewal, full feature):** a new payment type for renewals; an eligibility
  service that always checks live plan-entitlement dates rather than a cached status field; a new,
  additive code path in the payment-processing integration that doesn't touch existing purchase or
  upgrade flows; a new checkout endpoint; over 50 new tests, all green.
- **Done (Tuesday — two real bugs found the day after shipping):** a sidebar view still not
  excluding past-due/expired plans; a new checkout endpoint mounted under the wrong route prefix,
  causing every real request to it to fail.
- **Done (Wednesday — closing out past-due enforcement + a write guard):** enforcement merged
  across the app's product areas, always-on with no per-area rollback flag; a read/write mode
  parameter added to the existing project-access guard; a real write-path guard gap closed in one
  more product area, with route-level integration tests.
- **Done (Thursday — closing the "expired project" content gate on the backend):** a read guard
  that blocks only a project that is *fully* expired (not merely past-due), covering the real
  content-serving routes across every product area; the same class of gap found the previous
  week — a legacy, still-mounted route serving content with no guard at all — found again in a
  different route this week, again by an automated security review rather than a self-review.
- **Technical decisions:**
  - Retire the per-area rollback flags on the enforcement guard once it's always-on — the real
    rollback path becomes version control, not a runtime switch.
  - Make the read guard strictly narrower than the write guard (only a fully-expired project, not
    merely past-due) so it never competes with the past-due UI.
- **Mistakes (root cause):** two real bugs surfaced the day after shipping a feature whose test
  suite covered its business logic but not its route wiring or its interaction with an existing,
  adjacent view — neither was caught before merge. A legacy, deprecated route serving guarded
  content without the guard is the second time in two weeks the same shape has been found by an
  automated review, not a self-review.
- **What I learned:** tests that verify business logic in isolation don't prove an endpoint is
  reachable at its documented URL — that needs its own explicit check.
- **Where I'm weak:** "legacy routes left unguarded" was already flagged as a pattern last week and
  recurred this week in a different guard — there's still no systematic sweep of every mounted
  route (guarded or not) before calling a guard feature complete; an automated reviewer keeps
  finding it instead of a deliberate checklist.
- **Next-week focus:** an explicit legacy/deprecated-route sweep on every new guard before
  requesting review, instead of relying on an automated reviewer to catch it; verify a new
  endpoint actually responds at its documented URL as part of the review checklist, not just that
  its logic passes tests.

## Backend — architecture rebuild (fintech SaaS platform — client)

**New to this tracking this week.** A separate backend, being rebuilt from scratch on a cleaner
architecture (hexagonal / vertical-slice), meant to eventually replace the MVP backend above. Most
of its auth module so far was written by a teammate; my own first week of work on it landed
Friday, alongside the frontend cutover above.

- **Done:** a session identifier exposed through login/refresh so a client can track it; a wider
  registration payload (a couple of additional contact fields, one made required) plus an audit
  record for a required legal consent; a real bug found while verifying that work live — profile
  fields beyond a small hardcoded set were being silently dropped when read back, confirmed
  against a real registered user and the raw stored row; a container networking fix; a message-
  queue misconfiguration that made a best-effort background email step block for ~19 seconds per
  request, fixed down to a fraction of a second; a rename of roughly two dozen legacy-named
  database columns to clean names — **reverted the same day** (see mistakes).
- **Technical decisions:**
  - Pull a couple of newly-added profile fields out of a schemaless JSON blob into their own typed
    columns, instead of letting that blob keep growing.
  - Use an ORM-level column alias so application code can keep clean, readable names while the
    physical database column keeps its old name — after discovering why the physical name had to
    stay.
- **Mistakes (root cause):** a same-day rename of ~23 legacy-named database columns to clean names
  passed its own full test suite and merged — but violated an unwritten constraint no test in this
  codebase covered: this database's schema has to stay physically identical to the MVP backend's,
  because both systems point at the same database during the migration. Same root cause as the
  previous week's retrospective: writing a first attempt that's "correct in isolation" without
  verifying it against a real, external constraint before merging. Fixed the same day with a
  follow-up migration that reverted the physical column names while keeping the clean names at the
  application level via aliasing.
- **What I learned:** a rename that passes a codebase's own ~1,100 tests can still break a
  contract none of those tests cover — cross-system compatibility isn't an implicit guarantee,
  it needs an explicit check before touching shared schema.
- **Where I'm weak:** this is the exact pattern the previous week's retrospective called out —
  verify a real constraint before writing, not after — and it recurred this week, in a different
  codebase, on day one of real work there. Not a new lesson; the same one still isn't installed as
  a habit.
- **Next-week focus:** verify any schema change here against the MVP backend explicitly (or add a
  compatibility test) before merging, instead of finding out after; keep following up on the real
  intermittent login bug found this week and not yet fixed.

## Global retrospective

- **Pattern of the week:** the same underlying mistake showed up in two different codebases —
  writing a first attempt (a guard, a column rename, an error handler) against something "correct
  in isolation" without verifying it against a real, external constraint (mounted-route reality,
  cross-system schema compatibility, every call site of an existing pattern) before merging. On the
  MVP backend: two post-deploy wiring bugs plus a legacy unguarded route, second time in two weeks.
  On the new backend: a column rename that broke cross-system compatibility, reverted same day. On
  the frontend: two more instances of a silent-failure shape already flagged as debt the previous
  week.
- **Habit to change:** unchanged from the previous week's retrospective, and still not installed —
  before merging a change that looks correct in isolation (its own tests green), explicitly verify
  it against the real constraint that lives outside the change itself (another system, actual
  routing, every existing call site of a pattern) instead of trusting local test coverage alone.
- **New context:** first week with the architecture-rebuild backend in this tracking — Friday's
  work marks the real start of that migration, with the first production surface now running
  against it. The MVP backend still carries the real business load this week (renewal,
  entitlement, and expiration all shipped as complete features), but focus is starting to split
  across both backends.
- **Logged debt:** one pull request left open at week's end (the auth-client cutover); a real,
  intermittent login bug found but not yet fixed on the new backend; a pending sweep for remaining
  silent-failure call sites on the frontend; a pending systematic sweep for legacy unguarded routes
  on the MVP backend.
