# Week 2026-W32 (Mon Aug 3 – Fri Aug 7)

The **largest feature shipped end-to-end so far in this tracking period**: a full payment-past-due
entitlement system — backend across two days, complete frontend in a third — on top of three
pagination/search features shipped Tuesday-Wednesday and an unplanned infrastructure investigation (a
container build silently broken for 9 days) resolved the same day it surfaced. Unlike the previous
week, which closed with six pull requests open, this week closes with only **two** — both documented on
purpose as carryover, not lost. The underlying pattern: every larger feature got its own design/decision
session before the first commit (a spec with explicit architecture decisions, reviewed and approved) and
its own test suite — neither got skipped even on the highest-volume day (Wednesday, the busiest of the
week).

## Frontend / client SDK (fintech SaaS platform — client)

- **Done (Monday — checkout-return fix + 2 real payment-SDK bugs):** wired an in-app browser flow with
  server-side payment verification (never trusting the returning browser as proof of payment); two
  fixes in a row for the same real bug (a payment SDK's response object doesn't behave like a plain
  dict), found on a real device, not in mocks.
- **Done (Tuesday — closed checkout-return + 3 real user-facing bugs + started pagination):** merged
  the checkout fix; an auth bug blocking new-user invites; a purchase-flow contract bug (bad input
  handling plus wrong field names); a client-assignment action migrated to the correct dedicated
  endpoint after comparing against an older, proven codebase; started a pagination feature designed
  architecture-first.
- **Done (Wednesday — busiest day: 5 pagination pull requests + a same-day web+mobile search feature +
  an infrastructure fix):** shipped mobile pagination; a real progress-percentage fix; a complete
  name-search feature on web (73 tests, a real race condition caught and fixed in review) and a full
  mobile port built against mobile's own architecture the same day (91 tests); an unplanned
  investigation into six real bugs in a container build broken for over a week.
- **Done (Friday — entitlement SDK + full frontend for payment-past-due):** a shared domain policy; a
  payment-required error type mapped identically across four SDKs; a cached entitlement hook, a status-
  badge fix, and a global banner; a payment-required intercept wired into every real write action; a
  final UX fix connecting a "pay now" button to the actual upgrade flow instead of a plain redirect.
- **Technical decisions:**
  - Design against each platform's real architecture instead of literally porting a pattern across
    platforms — the mobile search implementation ended up genuinely different and worked on the first
    try.
  - Map a new error type identically across every product-area SDK — one check works everywhere
    instead of four different detection paths.
- **Mistakes (root cause):** Monday's two payment-SDK bugs are the same pattern twice in a row —
  assuming a third-party SDK object behaves like a plain dict without verifying against a real instance
  first. Tuesday's three bugs share a different root: code that assumed an API contract without
  verifying it against the real backend or an older, proven implementation.
- **What I learned:** an error handler that swallows a failure without logging it makes the next real
  bug much slower to diagnose — worth treating as immediate debt, not something fixed only after it
  actively hurts.
- **Where I'm weak:** the container build was broken for 9 days before anyone ran a real end-to-end
  build-and-run — none of the six bugs were hard to find, they just weren't exercised since the previous
  week. This codebase still lacks a periodic real build verification, not just trusting that code
  "looks right" in review.
- **Next-week focus:** merge the pending "pay now" UX fix; close the pending end-to-end test for the
  entitlement feature once the corresponding backend work is verified; put some periodic (or CI-
  blocking) real build-and-run check in place so a multi-day blind spot doesn't repeat.

## Backend (fintech SaaS platform — client)

- **Done (Monday — checkout return):** centralized return-URL handling and added a verification
  endpoint the app already called but that never existed; two real payment-SDK bugs found and fixed
  the same day.
- **Done (Tuesday — started pagination):** two endpoints that returned entire result sets
  unconditionally, confirmed via logs against a real account with 17 records — both given proper
  limit/cursor pagination.
- **Done (Wednesday — closed pagination + a real progress bug):** merged Tuesday's pagination work with
  its checklist run first; a real percentage calculation replacing a boolean disguised as a percentage,
  reusing an existing helper with no new performance cost.
- **Done (Thursday — full foundation of the payment-past-due feature, the biggest of the week):** a
  spec with seven architecture-decision records, approved before the first commit; a new status value
  with a legacy-alias bug caught and fixed the same day; an entitlement service (always derived from
  live dates, never a stored status) with 16 tests; a scheduled-job branch for the past-due-to-expired
  transition; a reusable HTTP-402 guard with 10 tests plus a contract test covering 76 routes; two of
  four product areas connected; a deliberate, documented pause to shift focus to frontend on Friday.
- **Done (Friday — closed all four product areas + notification):** the last two areas connected; a
  design mistake in one area's guard caught live in review and reverted the same morning; the last
  pending resolver closes out the first area fully; the rollout feature flag removed as redundant; an
  idempotent transition-notification email shipped.
- **Technical decisions:**
  - A reusable guard with swappable resolution strategies: one blocking algorithm, the only variation
    per route is how it finds which project is affected — avoids four near-duplicate implementations.
  - Entitlement always derived from live dates, never a stored status field — removes the clock window
    between a scheduled job and a webhook where displayed state could be wrong.
  - Remove a rollout feature flag once test coverage makes it redundant — the real rollback becomes
    version control, per pull request, per area.
- **Mistakes (root cause):** a legacy status alias was a real regression I introduced myself in the
  first pass of a new status enum, without checking the real values already stored in the database
  first. A guard implementation was written twice in one morning from a too-quick reading of a design
  note (conflating "this route skips user validation" with "this route can't carry this kind of guard").
- **What I learned:** a non-blocking CI check, or a rollout feature flag, can create a false sense of
  safety — neither substitutes for real verification (a real build-and-run, real test coverage) against
  the real system.
- **Where I'm weak:** both self-introduced-regression cases this week (the status alias, the guard
  rewrite) share the same pattern: writing the first attempt against an assumption instead of the real
  source of truth (actual database values, the full text of a design note). The fix came quickly both
  times, but after the fact, not before.
- **Next-week focus:** close the pending end-to-end test and merge the enforcement rollout pull request;
  check whether the "verify the assumption before writing, not after" pattern shows up anywhere else in
  this feature before considering it fully closed.

## Global retrospective

- **Pattern of the week:** every larger feature (checkout return, pagination, search, entitlement)
  followed the same healthy cycle — an explicit-decisions spec before coding, its own test suite,
  real verification (device, direct requests, build-and-run) before calling it done — even on the
  busiest day. The real mistakes this week (the payment-SDK bugs, the status alias, the guard rewrite)
  share one root cause: writing a first attempt against an unverified assumption instead of the real
  system or document, caught quickly but after the fact.
- **Habit to change:** before writing a first attempt at a fix, or a new status/guard, verify the real
  source (a live object, a real database column, the full text of a design note) — not after the first
  attempt fails. That happened three times this week with the same shape.
- **Logged debt:** 2 pull requests still open at week's end, 1 pending end-to-end test issue — all
  documented on purpose with a clear resume point, unlike the open-ended carryover from the previous
  week.
