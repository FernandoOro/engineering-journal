# Week 2026-W30 (Mon Jul 20 – Fri Jul 24)

The **highest feature-shipping volume of the last 6 weeks** — a complete plan-management modal, a
plan-upgrade flow, a global members/collaborators roster, a full marketing-calendar feature, and a
multi-conversation chat feature spanning backend, SDK, and frontend — with several pull requests
still moving through review by week's end, spread across two repositories. Each individual day was
well executed: spec-first, root-caused rather than symptom-patched, and verified live at nearly every
step. The pace of opening new work outran the pace of closing it out from midweek on.

## Frontend / client SDK (fintech SaaS platform — client)

- **Done (Monday — plan-management modal + upgrade flow + 4 bugs):** a two-level modal (plan summary
  → delete plan | manage seats/clients) with a full client-side data layer, availability-based
  gating, and a remove-member action. A third "upgrade plan" option surfaced 4 real bugs within 40
  minutes of testing against a real plan: a 404 from a missing route detail, a crash on nullable
  pricing fields, a duplicate-option listing, and a filter corrected twice because the first pass
  used the wrong signal.
- **Done (Tuesday — members roster, 2 compounding bugs):** fixed a members card that was scoped to a
  single project instead of a global roster, plus a missing refresh call on 3 of 4 mutating actions.
- **Done (Thursday — collaboration model + multi-conversation frontend, the busiest day):** proposed
  and adopted a new branch-integration model for the team; built an active-project store (refined
  after a code-review pass); shipped the client SDK and real per-conversation routing for a chat
  feature, replacing a temporary single-thread workaround and fixing a rate-limit bypass along the
  way. Several pull requests from this day were still in review by week's end.
- **Done (Friday — single-container Dockerization):** one container image for 4 web applications with
  a reverse proxy, process supervisor, and CI/deploy pipelines. Local build verification stayed
  incomplete — 3 attempts blocked by unreliable sandbox networking, not by the container definition.
- **Technical decisions:**
  - Gate UI features (upgrade eligibility, seat/client availability) on real backend availability
    instead of a plan-type field — more robust because it doesn't depend on that field continuing to
    mean the same thing tomorrow.
  - Centralize a shared piece of state's write path into one hook instead of each call site, after a
    code-review observation — the same "single source of truth" principle learned the previous week.
- **Mistakes (root cause):** the 404 in the upgrade-eligibility check was born in the **spec**, not
  the code — the initial research never validated a route detail against the real running server, and
  the implementation faithfully inherited the mistake. A pricing-filter fix was applied twice because
  the first pass knowingly used a signal that was already flagged as the wrong one, taken as a
  shortcut anyway.
- **What I learned:** spec-driven development only protects against bugs if the spec itself gets
  validated against the real running system, not just documented from a reading of the code.
- **Where I'm weak:** by week's end, several pull requests across both repositories were still moving
  through review rather than merged — fast, well-scoped, spec-first work is only half the job until
  it actually lands.
- **Next-week focus:** prioritize finishing verification and merging what's already open before
  starting new branches; get a network-reliable build verification for the Dockerization work.

## Backend (fintech SaaS platform — client)

- **Done (Monday — dead code masking a pricing error):** a cost-calculation function had an
  unconditional early return sitting at the same indentation as its intended fallback, so undefined
  upgrade combinations silently returned an empty result instead of a clear error.
- **Done (Tuesday — a repaired test + a new global roster endpoint):** repaired an integration test
  that had been silently testing nothing since a prior security change altered the endpoint's
  contract; shipped a new endpoint aggregating collaborators across every related project, plus an
  owner-exclusion fix.
- **Done (Wednesday — a full marketing-calendar feature + a real truncation bug):** two write paths —
  automated pre-population plus a stable claim mechanism — replacing a click-only flow and a fragile
  client-computed identifier; a read endpoint; routed a scheduled sync through an existing
  multi-provider LLM fallback system; found and fixed a real token-budget bug causing response
  truncation, verified live against a real fallback provider — full end-to-end confirmation still
  pending on the primary provider's outage being resolved.
- **Done (Thursday — multi-conversation, 6 layers in one morning + a production fix):** the full data
  model, migration (additive, not yet applied to any live database), data-access layer, services, and
  endpoints for a multi-conversation feature — opened for review with its verification checklist
  still in progress. In the afternoon, a real production fix: an LLM-provider fallback system's own
  protection function existed and was proven elsewhere in the codebase, but was never wired into the
  3 places that actually needed it — opened for review with a passing regression-test suite.
- **Done (Friday):** branch housekeeping only, no new code.
- **Technical decisions:**
  - Filter noise (a caller's own rows) at the route handler rather than inside a shared, generic
    helper, so the helper stays reusable for views that legitimately want to show that data.
  - Route a status flag through a dedicated module that deliberately bypasses a shared manager
    function, avoiding a hidden side effect the shared path would otherwise trigger.
- **Mistakes (root cause):** a broken integration test had likely been silently passing-but-testing-
  nothing for some time after a security change altered the endpoint's contract, without the test
  being updated to match. The provider-fallback bug is a pattern that's shown up in previous weeks: a
  correct function that only protects the system if it's actually called from every real place that
  needs it, not just the one it was originally written for.
- **What I learned:** a provider outage can hide a second, independent bug behind it — worth
  continuing to investigate even after finding an "obvious" cause for the surface symptom.
- **Where I'm weak:** two large features this week reached the review stage with real verification
  still incomplete — one because of an external outage outside my control, the other with no external
  blocker at all, just a checklist not yet worked through.
- **Next-week focus:** finish the verification checklist and apply the pending migration for the
  multi-conversation feature; re-verify the token-budget fix once the primary provider recovers;
  check whether the "protection function not wired everywhere" pattern shows up elsewhere in the
  fallback system.

## Global retrospective

- **Pattern of the week:** every individual day was well executed — spec-first, root-caused, verified
  live at nearly every step — but the volume of new work opened from midweek on outpaced what closed
  out in the same window. The busiest day of the week (two full features plus a production fix across
  three repositories) didn't close out a single pull request.
- **Habit to change:** before opening the next branch, prioritize finishing verification on — and
  merging — at least one of the pull requests already open. High output only compounds once it lands.
- **Logged debt:** several pull requests still in review across both repositories; one infrastructure
  spec not yet committed; a token-budget fix pending re-verification once a third-party outage
  resolves; an additive database migration pending an apply step.
